Deployment Process
Sprint release
Every merge into develop  deploys to Test automatically, several times a day. No approval, no
tag, no announcement — that is the point.
The smoke check calls /health  and asserts it returns 200 and the commit sha it just
deployed. A deploy that does not verify itself is one you hear about from a student on Saturday
morning.
Final release
At the end of a sprint, develop  goes to main  and is tagged.
1. Open the release pull request, develop  → main . The description lists every ticket
included — that list becomes the release notes.
2. Check the pre-deploy list (below).
3. Merge and tagv0.<n>.0 .
4. Approve. DevOps and the PM, named in the pull request. This is the only manual gate in the
process, and it exists because it is the only deploy anyone outside the team sees.
5. Deploy — the tag goes to Staging, then to Production on approval. (Both pending MT-201 and
MT-202; today a final release stops at Test.)
6. Verify — smoke check, then the three main journeys by hand.
7. Announce in the Teams channel before the Sprint Review.
Pre-deploy checklist
[ ] Pipeline green on develop , including the authorization stage
[ ] Migrations reviewed by someone other than the author and backward compatible
[ ] No new configuration value missing from the target environment
[ ] No secret added to the repository, including in a reverted commit
[ ] Demo dry run done — the "it worked on my machine" catch
[ ] Someone available for the next hour
1 merge to develop → pipeline stages 1-6 → migrate → deploy → smoke check
One artifact, built once, promoted unchanged. A final release deploys the
same bytes that were on Test all sprint. If Test and Production needed
different builds, an environment difference has leaked into the code.

Variable Local Test Source Notes
1. Read once at start-up and validate then. A missing required value stops the process loudly; it
never defaults silently.
2. .env.example  is committed with every key and every value empty, so a new joiner knows
what to fill in without ever seeing a real one.
3. Changing a value in an environment is a change like any other — say so in the Teams channel,
because a config change that nobody announced looks exactly like a bug.
Secrets
Database Migrations
Every schema change is a reviewed file in the repository. No hand-edited databases, ever,
including on Test.
Migrations run against an empty database on every CI run, which makes every build a free
test of the migration path.
They are applied by the pipeline before the new code starts, never by a person.
Backwards-compatible for one release (see Rollback).
A destructive change is split in two: release n stops using the column, release n+1 drops it.

An untested restore is a belief, not a backup. The test is cheap — restore into a scratch
database and confirm a seeded account is intact — and it is the only way to find out that the
snapshot excludes something before you need it.
Note also that a 7-day snapshot window and the 7-day erasure obligation interact: an account
deleted today still exists in snapshots for a week, which is why the erasure requirement is
written as within seven days rather than immediately.
